# Project instructions

## Product and stack

- This repository plans and builds a mobile-first community platform, initially oriented around study and interest groups. Read `Community_Platform_Concept.md` and `plan/ROADMAP.md` before changing scope or architecture.
- Mobile: React Native with Expo and TypeScript; target both iOS and Android.
- Backend: Python with FastAPI.
- Database: PostgreSQL. Use Alembic for every schema change; never treat ORM auto-create or manual production SQL as the migration workflow.
- Mobile clients communicate with the backend API. They must never connect directly to PostgreSQL.
- Keep provider choices replaceable until the provider-selection phase is completed. Do not add cloud credentials or secrets to the repository.

## Architecture and code quality

- Keep mobile, backend, infrastructure, and planning concerns clearly separated. Within the backend, keep HTTP routing, validation schemas, business services, persistence, and domain models separate.
- Keep the mobile API client and runtime configuration centralized. Screens/components must not hardcode API hosts or call `fetch` ad hoc.
- Keep feature code cohesive and avoid premature microservices. Prefer a modular monolith for the API until measured scale or team needs justify a split.
- Validate untrusted input at API boundaries, enforce authorization on the server, and return only fields the caller is allowed to see.
- Make loading, empty, error, offline, and permission-denied states part of each user-facing flow. Follow accessibility and platform conventions.
- Use formatting, linting, static typing, tests, dependency lockfiles, and small reviewable changes. Add tests alongside each feature, including negative authorization and failure cases.
- Do not claim a feature is production-ready until its security, observability, backup/recovery, migration, and rollback implications have been considered.

## Configuration and tunnel URLs

- The tracked mobile URL template is `mobile/.env.example`. Copy it to the ignored `mobile/.env.development.local` and edit the API URL there when a backend tunnel URL changes.
- Read public mobile settings through one typed configuration module (planned as `mobile/src/config/env.ts`); API clients must use that module. Do not scatter base URLs across screens.
- Expo's development-server/tunnel URL is generated by the Expo CLI when the server starts; it is not the backend URL and should not be hardcoded in app configuration. A shared mobile session needs both a reachable Expo development server and a separately reachable backend API.
- A physical device cannot use its own `localhost` to reach the developer's computer. Use a LAN-reachable address or an HTTPS backend tunnel as appropriate.
- Anything named `EXPO_PUBLIC_*` is bundled into the client and must be considered public. Never put database credentials, signing secrets, private API keys, or other secrets in mobile environment variables.
- Keep `.env` values out of Git. Update the template when configuration keys change; do not commit local tunnel URLs.

## Database and migrations

- Every database schema change requires an Alembic revision with a meaningful description and review of its generated SQL.
- Test upgrades from the prior schema and, where feasible, downgrade/restore behavior. Prefer backward-compatible expand/contract changes for rolling deployments.
- Production migrations are an explicit, observable deployment step and must not run concurrently from every API replica.
- Add indexes and constraints based on query patterns and invariants; document data-retention and deletion behavior for user-generated content.

## Git, reviews, and delivery

- Follow the branch and promotion model in `plan/ROADMAP.md`. Use short-lived, descriptive branches, pull requests, required CI checks, and reviewable commits.
- Use Conventional Commit-style messages, for example `feat(communities): add invite links` or `fix(auth): reject expired refresh tokens`.
- Never commit secrets, user data, production dumps, build artifacts, or generated credentials.
- CI must validate the mobile and backend independently and run database-backed tests where relevant. Deployments must use separate development, staging, and production configuration/secrets and explicit promotion gates.
- Mobile production delivery means signed iOS/Android builds and store distribution; backend/API deployment is a separate pipeline. Do not confuse an Expo development tunnel with production hosting.

## Planning discipline

- Keep `plan/ROADMAP.md` as the cumulative source of truth and maintain the matching phase documents under `plan/phases/`.
- Build all agreed product capabilities in phases; do not silently drop voice, moderation, files, reminders, room reservations, or engagement features from scope.
- Record unresolved product/provider decisions as explicit decisions to make, with a phase gate. Do not invent a vendor, legal policy, pricing model, or moderation policy as if it were confirmed.
- When implementation begins, update phase status and acceptance criteria as work is completed.
